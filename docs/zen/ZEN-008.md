# ZEN-008: Interface RPC JSON do node (controle local)

`final` · `interface-local` (não é consenso — ver nota abaixo)

## Resumo

Define o formato de requisição/resposta da RPC JSON que um node Zhu expõe
em `127.0.0.1` para ser controlado (CLI, ou qualquer cliente próprio —
wallet gráfica, explorer local) enquanto está em execução. Não é uma regra
de consenso: dois nodes com RPCs diferentes continuam na mesma rede P2P
sem problema. É documentado como ZEN porque, ao contrário de um `SPEC.md`
interno, **qualquer cliente que não seja este binário Go** (outra
linguagem, outro processo) precisa deste contrato exato para falar com o
node.

## Motivação

O storage (bbolt) do node é single-writer: só um processo pode ter o banco
aberto para escrita. Isso significa que um comando de CLI como `balance` ou
`send` não pode abrir o banco diretamente enquanto `node run` está ativo —
ele precisa perguntar ao processo do node, que é o único dono do banco
naquele momento. A RPC existe **por isso**, não como conveniência: é o
único jeito de consultar ou movimentar fundos com o node ligado.

## Especificação

### Transporte e bind

- `net/http` puro (sem framework), método `POST`, endpoint `/rpc`.
- **Bind exclusivo em loopback** (`127.0.0.1`) — o node **recusa** subir a
  RPC em qualquer endereço que não seja loopback. Não é uma API pública:
  é a interface de controle do *dono* do node. Não há autenticação porque
  não há como alcançar a porta de fora sem já ter acesso à máquina.
- Sem TLS — tráfego é loopback, nunca sai da máquina.

### Envelope de requisição/resposta

```
Requisição:  POST /rpc   {"method": "<nome>", "params": {...}}
Sucesso:                  {"result": <valor>}
Erro:                      {"error": {"code": <int>, "message": "<string>"}}
```

Todo método usa o mesmo envelope de erro `{code, message}` — não há
formato de erro diferente por método.

### Métodos

| Método | Params | Result | Observação |
|--------|--------|--------|------------|
| `getinfo` | — | altura, hash do tip, contagem de peers, tamanho do mempool, hashrate do miner local | visão geral do node |
| `getbalance` | `address` | saldo em subunidades | soma dos UTXOs não gastos do endereço |
| `getnewutxos` | `address` | lista de UTXOs do endereço | usado pelo wallet builder (ZEN-001/wallet) para montar uma tx |
| `sendrawtx` | `hex` (tx serializada canônica, ZEN-001) | txid | injeta uma transação já assinada, sem usar a wallet do datadir |
| `sendtoaddress` | `to`, `amount` | txid | usa a wallet do datadir do node para montar, assinar e enviar |

### CLI de referência

```
node info    --rpc 127.0.0.1:8551
node balance --rpc 127.0.0.1:8551 [--address P...]
node send    --rpc 127.0.0.1:8551 --to P... --amount 1.5
```

Cada subcomando é uma chamada RPC fina — qualquer cliente (não só este
CLI) que fale o envelope acima pode substituir essas chamadas.

## Casos de erro

- Node não está rodando (conexão recusada na porta RPC) → cliente deve
  reportar de forma clara que não há node ativo naquele endereço, não um
  erro de rede genérico.
- `send`/`sendtoaddress` sem wallet no datadir → erro instruindo a criar
  uma wallet primeiro (não uma falha silenciosa).
- Tentativa de bind da RPC fora de loopback → o node recusa subir e
  encerra com mensagem clara (não faz downgrade silencioso para loopback).
- `sendrawtx` com hex malformado ou tx estruturalmente inválida (ZEN-001)
  → erro no envelope `{code, message}`, nunca 500 genérico sem corpo.

## Compatibilidade

Como não é consenso, um node pode adicionar métodos novos livremente
(aditivo). Remover um método ou mudar a forma de `params`/`result` de um
método existente quebra qualquer cliente externo que dependa dele — deve
ser tratado como mudança incompatível de interface (não precisa de
coordenação de rede, mas quebra scripts/CLIs/GUIs existentes) e, se
relevante, documentado com uma nota de versão neste ZEN.
