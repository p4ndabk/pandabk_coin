# ZEN-001: Formato canônico de bloco e transação

`final`

## Resumo

Define os bytes exatos de um `Header`, `Tx` e `Block` na rede Zhu, os dois
hashes de identidade (ID do bloco e TxID), a merkle root, e o formato de
endereço. Qualquer implementação que produza esses bytes de forma diferente
não interopera com a rede — dois nós só concordam sobre um bloco se
serializarem os mesmos campos exatamente nos mesmos bytes.

## Motivação

`encoding/gob`, `encoding/json` e a maioria dos serializadores genéricos não
garantem ordem estável de campos nem representação única de um número — o
mesmo bloco lógico poderia virar bytes diferentes em duas implementações, logo
hashes diferentes, logo dois nós divergindo sobre se um bloco existe. Este ZEN
fixa um formato big-endian hand-rolled, campo a campo, para que
`struct → bytes` seja uma função total e determinística em qualquer
linguagem.

## Especificação

### Header (96 bytes, tamanho fixo)

| Offset | Campo | Tipo | Tamanho |
|-------:|-------|------|--------:|
| 0 | Version | uint32 BE | 4 |
| 4 | Height | uint64 BE | 8 |
| 12 | PrevHash | bytes | 32 |
| 44 | MerkleRoot | bytes | 32 |
| 76 | Timestamp | int64 BE | 8 |
| 84 | Bits | uint32 BE | 4 (nBits compacto, ver ZEN-002) |
| 88 | Nonce | uint64 BE | 8 |

Total: 96 bytes. Campos de largura fixa (sem varint no header) tornam o
parsing trivial e à prova de ambiguidade de comprimento.

**ID do bloco = SHA-256d(Header.Bytes())** — SHA-256 aplicado duas vezes
sobre os 96 bytes do header. É o identificador barato usado para indexar e
encadear blocos; **não** é o hash usado na checagem de proof of work (esse é
Argon2id, ver ZEN-002) — são dois hashes com papéis deliberadamente
separados: SHA-256d é barato e usado para todo lookup/referência; Argon2id é
caro e roda só na validação de PoW do bloco completo.

### Block

```
Block { Header; Txs []Tx }
```

`Txs[0]` deve ser a coinbase (única exceção às regras normais de transação —
ver ZEN-003 para a regra de validação completa).

### Tx / TxIn / TxOut

| Tipo | Campos |
|------|--------|
| `OutPoint` | `TxID [32]byte`, `Index uint32` |
| `TxIn` | `Prev OutPoint`, `Sig []byte` (ASN.1 DER), `PubKey []byte` (33 bytes, comprimida) |
| `TxOut` | `Value uint64` (subunidades, 1 ZHU = 1e8), `PubKeyHash [20]byte` |
| `Tx` | `Version uint32`, `Ins []TxIn`, `Outs []TxOut` |

**TxID = SHA-256d(Tx serializada canônica).**

**Coinbase** (a transação que abre cada bloco, cria a recompensa): exatamente
1 input, com `Prev = {TxID: zero, Index: 0xffffffff}`; o campo `PubKey` desse
input carrega `height ‖ extranonce` (não uma chave pública real — estilo
BIP34) para garantir que o TxID seja único por altura. Sem isso, duas
coinbases pagando o mesmo endereço com o mesmo valor teriam o mesmo TxID e
colidiriam no índice de UTXO.

**Modelo de gasto — pay-to-pubkey-hash estrutural, sem scripts:** não existe
máquina de scripts (ao contrário do Bitcoin Script). Um `TxOut` trava um
valor a um `PubKeyHash`; gastá-lo exige um `TxIn` cujo `PubKey` hasheia
(`SHA-256(PubKey)[:20]`) para aquele mesmo `PubKeyHash`, com uma assinatura
válida sobre o sighash (abaixo).

### Sighash (o que é assinado)

`SigHash(i, prevPKH)` = **SHA-256d** da transação inteira serializada, com
duas substituições aplicadas antes de hashear:

1. O campo `Sig` do input `i` (e de todos os outros inputs) é tratado como
   vazio.
2. O slot de `PubKey` do input `i` é substituído pelo `PubKeyHash` (20 bytes)
   do output que esse input está gastando.

Assinatura: ECDSA sobre a curva P-256 (`crypto/ecdsa`, `SignASN1`/
`VerifyASN1` da stdlib Go — primitiva auditada, não hand-rolled). É um único
modo de assinatura, equivalente a SIGHASH_ALL do Bitcoin (assina sempre a
transação inteira): menos modos de sighash é menos regra de consenso para
errar.

### Merkle root

Sobre a lista de TxIDs do bloco (não sobre as txs inteiras):

- 0 transações: bloco inválido (a coinbase é obrigatória — ver ZEN-003).
- 1 transação: root = o próprio TxID.
- N ímpar em qualquer nível da árvore: duplica o último elemento do nível
  antes de parear (convenção idêntica ao Bitcoin).
- Cada par é combinado como `SHA-256d(esquerda ‖ direita)`, subindo até
  restar um único hash de 32 bytes — a `MerkleRoot` do header.

Qualquer transação alterada muda a raiz, que muda o hash do header, que
quebra o encadeamento da cadeia.

### Endereço (Base58Check, versão `0x37`)

```
address = Base58( 0x37 ‖ SHA-256(pubkey comprimida 33B)[:20] ‖ checksum )
checksum = SHA-256d( 0x37 ‖ pubkeyhash )[:4]
```

- **Hash do endereço**: SHA-256 truncado a 20 bytes (não RIPEMD-160 — evita
  uma primitiva depreciada por uma já auditada na stdlib, ao custo de não ser
  bit-a-bit igual ao Bitcoin).
- **Byte de versão `0x37`**: faz todo endereço Zhu começar com o caractere
  `P` em Base58 — identidade visual da rede.
- **Alfabeto Base58**: o mesmo do Bitcoin, evita caracteres ambíguos (`0`/`O`,
  `l`/`1`).
- **Checksum de 4 bytes** (SHA-256d dos bytes versão+hash, primeiros 4
  bytes): decodificar um endereço recalcula e compara o checksum e a versão;
  qualquer divergência é erro. Detecta erro de digitação **antes** de
  qualquer moeda ser enviada — um pagamento para um endereço inválido é
  irreversível, então essa validação barata no cliente é obrigatória.

## Casos de erro

- Decodificar bytes truncados ou corrompidos de Header/Tx/Block → erro,
  nunca panic.
- Endereço com checksum inválido ou byte de versão diferente de `0x37` →
  erro, endereço rejeitado.
- Tx com 0 inputs ou 0 outputs → inválida estruturalmente (rejeitar antes de
  qualquer outra checagem).
- Merkle de bloco sem transações → bloco inválido (todo bloco precisa de ao
  menos a coinbase).

## Compatibilidade

Regra fundacional — qualquer mudança de layout de bytes, de algoritmo de
hash (SHA-256d dos IDs, merkle) ou do byte de versão do endereço é
incompatível com a rede existente (hard fork / rede nova). Extensões
aditivas (ex.: um novo tipo de output) exigem um ZEN próprio que preserve a
decodificação dos campos atuais.
