# ZEN-005: Parâmetros de consenso e política monetária

`final`

## Resumo

Define o conjunto fechado de números que precisam ser idênticos em todo node
para a rede concordar consigo mesma — recompensa por bloco, cronograma de
halving, tempo-alvo entre blocos, limites de tamanho e dificuldade — e como
perfis diferentes (devnet/testnet/mainnet, ou um build customizado) formam
redes distintas por construção.

## Motivação

Uma blockchain é um acordo entre máquinas que nunca se conheceram; se dois
nodes usarem números de consenso diferentes, rejeitam os blocos um do outro
e a rede se parte. Este ZEN é a fonte única desses números — qualquer
reimplementação precisa usar exatamente estes valores (por perfil) para
interoperar com a rede Zhu correspondente.

## Especificação

### Perfis

Um **perfil** é um conjunto completo de parâmetros de consenso, imutável
depois de fixado — perfis diferentes **são redes diferentes** (produzem
gêneses diferentes, ver abaixo), nunca uma opção de runtime dentro da mesma
rede.

| Perfil | Uso | Diferença principal |
|--------|-----|----------------------|
| `devnet` | rede de desenvolvimento padrão | bloco alvo 60s, halving a cada 1.000 blocos |
| `test` | testes automatizados | parte da base do devnet, mas Argon2 barato (1 MiB) para rodar em milissegundos; **não herda overrides de `build.conf`** — testes precisam de regras estáveis entre máquinas |
| `mainnet` | rede de produção | placeholder declarado nesta fase (bloco alvo 10 min); valores definitivos ainda não calibrados |

### Parâmetros (`Params`)

| Campo | Tipo | Valor (devnet) | Observação |
|-------|------|----------------|------------|
| `Name` | string | `"devnet"` | identifica o perfil |
| `TargetSpacing` | duration | 60s | tempo-alvo entre blocos |
| `RetargetInterval` | uint64 | 100 | blocos entre recálculos de dificuldade (ZEN-002) |
| `HalvingInterval` | uint64 | 1.000 | blocos entre halvings do subsídio |
| `InitialSubsidy` | uint64 | 5.000.000.000 subunidades (50 ZHU) | recompensa da coinbase na época 0 |
| `Argon2Mem` / `Argon2Time` / `Argon2Threads` | uint32/uint32/uint8 | 65536 KiB / 1 / 1 | ver ZEN-002 (perfil `test`: 1024 KiB) |
| `PowLimitBits` | uint32 | — | dificuldade mínima (target máximo) em nBits, ZEN-002 |
| `MaxClamp` | int64 | 4 | limite de ajuste por retarget: [¼×, 4×] (ZEN-002) |
| `CoinbaseMaturity` | uint64 | 10 | blocos até um output de coinbase poder ser gasto (ZEN-003) |
| `MaxBlockSize` | uint32 | 262144 (256 KiB) | **regra de consenso**: bloco serializado maior é inválido (ZEN-003) |
| `Genesis` | struct | — | timestamp, mensagem, `Bits`, nonce e hash esperado do bloco 0 |
| `DefaultPort` / `DefaultRPCPort` | string | `:9551` / `127.0.0.1:8555` | portas padrão de rede/RPC do perfil |
| `SeedPeers` | []string | — | peers iniciais do perfil, usados como seeds do address book (ZEN-004) |

**Subunidade inteira**: 1 ZHU = 1e8 subunidades, sempre `uint64`. Nunca ponto
flutuante — `float64` acumula erro de arredondamento, e dois nodes somando as
mesmas taxas em ordem diferente chegariam a saldos diferentes.

### Subsídio e emissão (halving)

```
BlockSubsidy(height) = InitialSubsidy >> (height / HalvingInterval)
```

Divisão inteira por deslocamento de bits; retorna 0 quando o shift zera o
valor (fim da emissão de novas moedas). Se o shift for ≥ 64, o resultado é 0
explicitamente (nunca undefined behavior de shift-overflow).

`MaxSupply()` é **derivado**, nunca hardcoded: soma `BlockSubsidy` por cada
época de halving até a emissão zerar. Um teto fixado à parte poderia
divergir de `BlockSubsidy` se um dos dois fosse editado sem o outro; derivar
garante que os dois concordam por definição. No perfil devnet, isso converge
para um supply máximo de aproximadamente 100.000 ZHU.

### Gênesis e identidade de rede

O bloco gênesis (altura 0) é **hardcoded por perfil** — mesmo timestamp,
mensagem, `Bits` e nonce em todo node do mesmo perfil, validado por hash
exato (ZEN-003) em vez das regras normais de bloco.

**Builds customizados derivam um gênesis diferente.** Quando os parâmetros
de um build (`TargetSpacing`, `HalvingInterval`, `InitialSubsidy`, etc.) são
fixados de forma diferente do perfil padrão, esses valores entram na
mensagem do bloco 0 e **mudam o hash do gênesis** — que é justamente o campo
`genesis` comparado no handshake P2P (ZEN-004). O efeito é intencional: um
binário com economia diferente forma uma **rede separada por construção** e
nunca se mistura por acidente com a rede do perfil oficial. É assim que
builds experimentais podem circular sem poluir a rede principal — a
separação não depende de ninguém lembrar de mudar um número de versão, ela é
uma consequência matemática de mudar qualquer parâmetro listado acima.

## Casos de erro

- Altura além do último halving (subsídio já chegou a 0) → `BlockSubsidy`
  retorna 0, sem panic, sem overflow.
- Shift de halving ≥ 64 bits → tratado explicitamente como subsídio 0.

## Compatibilidade

Qualquer mudança num valor deste ZEN para um perfil **já em uso** é
equivalente a criar uma rede nova (o gênesis muda, ver acima) — nunca uma
migração in-place. Adicionar um perfil novo é aditivo e não afeta os
existentes. Os valores de `mainnet` são explicitamente placeholder nesta
fase — um ZEN futuro deve fixá-los antes de qualquer lançamento de rede
principal, e a partir daí `mainnet` também se torna imutável por este
mesmo princípio.
