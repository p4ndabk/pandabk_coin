# ZEN-009: Cronograma de emissão em degraus com piso perpétuo

`draft` · `consenso` — substitui a política de halving geométrico descrita
em [ZEN-005](./ZEN-005.md#subsídio-e-emissão-halving)

## Resumo

Troca o halving geométrico (`subsídio ÷ 2` a cada época) por um **degrau
linear**: o subsídio da coinbase cai `SubsidyStepAmount` (1 ZHU) a cada
`SubsidyStepInterval` blocos, até atingir um **piso** (`MinSubsidy`, 5 ZHU)
— a partir daí o subsídio fica fixo em 5 ZHU **para sempre**. Ao contrário
do cronograma atual de `params` (ZEN-005), a emissão nunca chega a zero:
não existe mais um `MaxSupply()` finito.

## Motivação

Halving geométrico até zero (o modelo do Bitcoin) cria um ativo cuja
segurança de longuíssimo prazo depende inteiramente de taxas de transação
superarem a queda do subsídio — e um teto de emissão fixo tende a
incentivar açambarcamento (hold) em vez de circulação, o oposto de "um
node em cada casa, uma rede usada". Um piso perpétuo (o mesmo princípio do
**tail emission** do Monero) garante que sempre exista um subsídio mínimo
pagando quem sustenta a rede, e a queda linear (em vez de geométrica) é
mais previsível e mais fácil de explicar do que uma progressão geométrica.
Combinado com a queima estrutural de [ZEN-010](./ZEN-010.md), a emissão
perpétua deixa de significar inflação sem controle: o que o piso emite, o
uso real da rede (posts, salas, curtidas) pode queimar de volta.

## Especificação

### Parâmetros (substituem `HalvingInterval` em `Params`)

| Campo | Tipo | Valor proposto (devnet) | Observação |
|-------|------|--------------------------|------------|
| `InitialSubsidy` | uint64 | 1.000.000.000 subunidades (10 ZHU) | subsídio na altura 0 (já existe, valor muda de 50 → 10 ZHU) |
| `SubsidyStepAmount` | uint64 | 100.000.000 subunidades (1 ZHU) | quanto o subsídio cai a cada degrau |
| `SubsidyStepInterval` | uint64 | 1.000 blocos | blocos entre cada degrau — **fixado diretamente em altura de bloco**, não derivado de `TargetSpacing`/anos em runtime; o valor devnet segue a mesma escala didática do `HalvingInterval` atual (rápido o bastante para testar); um valor de mainnet equivalente a ~4 anos reais fica para quando o perfil `mainnet` (hoje placeholder, ZEN-005) for calibrado |
| `MinSubsidy` | uint64 | 500.000.000 subunidades (5 ZHU) | piso — subsídio nunca cai abaixo disso |

`HalvingInterval` é removido; `InitialSubsidy` é reaproveitado com valor
novo (10 ZHU em vez de 50 ZHU).

### `BlockSubsidy(height)`

```
maxSteps := (InitialSubsidy - MinSubsidy) / SubsidyStepAmount   // = 5 com os valores acima
steps    := height / SubsidyStepInterval
if steps >= maxSteps {
    return MinSubsidy
}
return InitialSubsidy - steps*SubsidyStepAmount
```

A guarda `steps >= maxSteps` evita subtração que cruzaria abaixo do piso
(sem depender de underflow de `uint64` para parar — checagem explícita,
mesma disciplina de `params` hoje para o halving).

### Tabela (devnet, `SubsidyStepInterval = 1000`)

| Altura | Subsídio |
|--------|----------|
| [0, 1000) | 10 ZHU |
| [1000, 2000) | 9 ZHU |
| [2000, 3000) | 8 ZHU |
| [3000, 4000) | 7 ZHU |
| [4000, 5000) | 6 ZHU |
| [5000, ∞) | 5 ZHU (perpétuo) |

### `MaxSupply()` deixa de ser finito

Hoje `MaxSupply()` (ZEN-005) é a soma do cronograma de halving — um valor
finito e derivado. Com piso perpétuo, o supply **diverge**: cresce
`MinSubsidy` por bloco, para sempre, depois da altura em que o piso é
atingido. A função deve ser substituída por duas derivadas finitas:

```
PreTailSupply() uint64   // soma de BlockSubsidy(h) para h em [0, maxSteps*SubsidyStepInterval) — finito, derivado
TailEmissionRate() uint64 // = MinSubsidy — quanto entra em circulação por bloco, para sempre, após o piso
```

A taxa de **inflação percentual** anual não é constante: `TailEmissionRate
× blocosPorAno ÷ supplyCirculante(t)` — decrescente ao longo do tempo à
medida que o supply acumulado cresce (mesma dinâmica assintótica do
Monero), mesmo a emissão nominal por bloco sendo constante.

## Casos de erro

- Altura muito grande (overflow de `steps*SubsidyStepInterval`) → a divisão
  inteira de `height / SubsidyStepInterval` não overflowa antes da
  comparação com `maxSteps`; nenhuma subtração é feita depois do piso
  atingido, então não há risco de `uint64` inverter para um número enorme.
- `SubsidyStepAmount` ou `SubsidyStepInterval` configurado como 0 num
  perfil customizado → configuração de perfil inválida, deve ser rejeitada
  na construção do `Params` (não na hora de minerar).

## Compatibilidade

**Hard fork / rede nova.** Isto muda o valor de `coinbase.value ≤
subsídio(altura) + Σ taxas` (regra 8 de ZEN-003) para toda altura — um
node com o `BlockSubsidy` antigo (halving geométrico) rejeita todo bloco
minerado por um node com esta regra, e vice-versa. Como qualquer mudança
de `params` (ZEN-005), muda o hash do gênesis por construção — vira rede
separada automaticamente, nunca uma migração in-place da rede devnet
atual.
