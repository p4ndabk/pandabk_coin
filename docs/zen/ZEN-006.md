# ZEN-006: Política de mempool e relay de transações

`final` · `política` (não é consenso — ver nota abaixo)

> **Nota:** se [ZEN-011](./ZEN-011.md) (`draft`) for implementado, a taxa
> deixa de ser renda do minerador (é queimada) — a ordenação por
> `feeRate` abaixo continua igual na prática, mas a motivação descrita
> ("é isso que o minerador embolsa") passa a ser só política de alocação
> de espaço de bloco contra spam, não incentivo econômico de quem
> minera.

## Resumo

Define as regras de admissão, ordenação e descarte de transações não
confirmadas no mempool de um node Zhu, e como essas transações são
oferecidas via `getmempool`/`inv` (ZEN-004) aos peers. Ao contrário dos
ZENs anteriores, isto **não é uma regra de consenso**: dois nodes com
políticas de mempool diferentes não se separam da rede — só relayam e
minerem txs de forma diferente. Ainda assim é protocolo, porque afeta o
que um node oferece a outro via `inv`/`getdata`/`getmempool`.

## Motivação

Entre o envio de uma transação e sua confirmação num bloco, ela precisa
viver em algum lugar e se espalhar pela rede antes que um minerador a
inclua. Sem uma política clara de admissão e descarte, um peer malicioso
poderia inundar o mempool de um node com transações inválidas ou
de baixo valor, consumindo memória sem limite. A política aqui é
deliberadamente simples — o mínimo que fecha os abusos óbvios sem a
complexidade de mecanismos como Replace-by-Fee (RBF) ou encadeamento de
transações não confirmadas.

## Especificação

### Admissão (`Add`)

Uma transação candidata é rejeitada, nesta ordem, se:

1. For uma coinbase (coinbases só existem dentro de blocos, nunca soltas
   no mempool).
2. O TxID já está presente no pool (duplicata).
3. Qualquer input referencia um outpoint que não existe no UTXO set atual
   da chain, ou que já foi gasto por um bloco confirmado.
4. Qualquer input referencia um outpoint **já reservado por outra
   transação pendente no mempool** (double-spend entre transações não
   confirmadas — rastreado por um índice `outpoint → txid` separado do
   pool principal, para responder em O(1) em vez de varrer o pool
   inteiro a cada admissão).
5. Assinatura de qualquer input é inválida (mesma verificação de
   ZEN-001/ZEN-003).
6. `Σ inputs < Σ outputs`.
7. Algum input gasta uma coinbase ainda não madura (`CoinbaseMaturity`,
   ZEN-005).

Se aceita, a taxa da transação é `Σ inputs − Σ outputs`, e o `feeRate` é
essa taxa dividida pelo tamanho serializado (ZEN-001) da transação.

**Não implementado, deliberadamente:**

- **Sem encadeamento de transações não confirmadas.** Uma transação que
  gasta o output de outra ainda no mempool (não confirmada) é rejeitada.
  Aceitar exigiria validar cadeias de dependência e removê-las em cascata
  se a base cair — complexidade que este ZEN explicitamente não cobre
  nesta versão. Quem quer gastar um output ainda não confirmado espera a
  confirmação.
- **Sem Replace-by-Fee (RBF).** Uma vez admitida, uma transação não é
  substituível por outra de taxa maior sobre os mesmos inputs.
- **Sem taxa mínima por política.** Qualquer taxa `≥ 0` é admitida — o
  corte real acontece só pelo limite de tamanho do pool (abaixo). Um piso
  fixo envelheceria mal; deixar o limite de tamanho fazer a triagem é
  auto-regulável pelo uso real da rede.

### Ordenação e limite de tamanho

- Transações são ordenadas por **taxa por byte** (`feeRate`), não por taxa
  absoluta — o recurso escasso é espaço no bloco (bytes, limitado por
  `MaxBlockSize`, ZEN-005), não a taxa em si.
- `TopByFeeRate(maxBytes)`: retorna transações em ordem decrescente de
  `feeRate` até encher o orçamento de bytes — é isso que um minerador usa
  para montar o próximo bloco, e é a mesma ordem usada na resposta a
  `getmempool` (ZEN-004: até 1.000 TxIDs, maior `feeRate` primeiro).
- Pool com limite de tamanho (ordem de 5.000 transações no perfil
  devnet): ao encher, uma transação nova com `feeRate` maior que a menor
  do pool evicta essa menor antes de ser admitida; se a nova tem
  `feeRate` menor ou igual à pior já presente, é rejeitada.

### Sincronização com a chain

- **Connect de bloco**: toda transação confirmada é removida do mempool;
  qualquer transação pendente que se tornou inválida por causa do bloco
  (um input dela foi gasto pelo bloco) também é removida.
- **Reorg** (ZEN-003): transações desconectadas do ramo abandonado voltam
  ao mempool via `Readd`, mas passam pela **mesma validação completa de
  `Add`** — o ramo vencedor pode ter gasto os mesmos inputs, então nunca
  se assume que uma tx que era válida no ramo antigo continua válida sem
  reverificar.

## Casos de erro

- Duas transações pendentes disputando o mesmo outpoint → a segunda é
  rejeitada com um erro específico de double-spend (não um erro genérico).
- Transação que gasta output de outra ainda não confirmada → rejeitada
  (limite declarado, não bug).
- Pool cheio e transação nova com `feeRate` pior que todas as presentes →
  rejeitada sem evict.

## Compatibilidade

Como não é regra de consenso, um node pode adotar uma política de mempool
mais restrita ou mais permissiva sem sair da rede — ele só vai relayar e
minerar um subconjunto diferente de transações válidas. Isso é aditivo e
seguro de mudar unilateralmente. O que **precisa** permanecer estável para
interoperar é o formato de resposta de `getmempool` (ZEN-004): TxIDs
ordenados por `feeRate` decrescente, até 1.000 por resposta.
