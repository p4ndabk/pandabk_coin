# ZEN-002: Proof of Work Argon2id — target e retarget

`final`

## Resumo

Define o algoritmo de proof of work da rede Zhu (Argon2id memory-hard, não
SHA-256), o formato compacto do alvo de dificuldade (`nBits`), o cálculo de
trabalho acumulado usado no fork choice (ZEN-003), e a fórmula de retarget
que mantém o tempo entre blocos estável.

## Motivação

SHA-256 é puro cálculo: um ASIC dedicado é ordens de magnitude mais eficiente
que uma CPU, e mineração com SHA-256 tende a centralizar em quem tem capital
para hardware especializado. Argon2id é **memory-hard**: cada hash exige
preencher e acessar aleatoriamente um bloco grande de RAM (64 MiB no perfil
devnet), com acessos que dependem de dados já escritos — sem atalho
paralelo. O gargalo vira banda de memória (commodity, não capital), e a
vantagem de hardware dedicado cai para algo que não paga o investimento. Um
notebook compete de igual com uma fazenda de mineração — é a decisão central
por trás do princípio "um node em cada casa".

## Especificação

### Hash de PoW

```
PowHash(headerBytes) = Argon2id(
    password = headerBytes,   // os 96 bytes do Header (ZEN-001)
    salt     = "zhubk/pow/v1",
    time     = Argon2Time,     // 1 no devnet
    memory   = Argon2Mem,      // 65536 KiB (64 MiB) no devnet; 1024 KiB no perfil test
    threads  = 1,               // sempre 1 — ver nota abaixo
    keyLen   = 32,
)
```

Os 32 bytes resultantes são interpretados como um inteiro **big-endian**. O
bloco é válido sob PoW se `PowHash < target` (o `target` derivado de `Bits`,
abaixo).

- **Variante `id`** (não `i` nem `d`): híbrido recomendado pela RFC 9106 para
  uso geral — equilíbrio entre resistência a canal lateral (força do `i`) e
  resistência a GPU (força do `d`).
- **Salt fixo `"zhubk/pow/v1"`, não por-bloco.** Aqui o salt é separador de
  domínio, não proteção de senha: fixá-lo faz o PoW ser função pura do
  header (todo node recalcula e confere o mesmo valor) e amarra o hash a
  *esta* rede especificamente — outro salt produziria hashes incompatíveis,
  ou seja, uma rede diferente. O sufixo `v1` reserva espaço para uma
  migração de salt versionada no futuro.
- **`Argon2Threads = 1` sempre**, independente de quantos workers de
  mineração o node roda em paralelo (isso é orquestração do pacote `miner`,
  fora deste ZEN). Se o número de threads entrasse no cálculo do próprio
  hash Argon2, o resultado dependeria do hardware de quem minerou e deixaria
  de ser verificável de forma determinística por quem tem outra máquina.

### nBits — formato compacto de dificuldade

O alvo (`target`) é um inteiro de até 256 bits; guardá-lo cru no header
custaria 32 bytes. Em vez disso, `Bits` (`uint32`, campo do Header) usa o
formato compacto do Bitcoin:

- 1 byte de expoente + 3 bytes de mantissa.
- `CompactToTarget(bits) *big.Int` e `TargetToCompact(target) uint32` são
  inversas para valores normalizados:
  `TargetToCompact(CompactToTarget(x)) == x`.

Um bloco nunca pode ter `target` acima de `PowLimitBits` (dificuldade mínima
da rede, parâmetro de perfil — ver ZEN-005).

### Trabalho (BlockWork)

```
BlockWork(bits) = 2^256 / (CompactToTarget(bits) + 1)
```

O **trabalho acumulado** de uma cadeia é a soma de `BlockWork` de cada bloco
nela — é o critério de fork choice (ZEN-003), **nunca a altura**: altura é
falsificável barato (basta encadear muitos blocos de dificuldade mínima);
trabalho reflete o custo real de energia e memória gasto e não pode ser
forjado sem realmente minerar.

### Retarget

A cada `RetargetInterval` blocos (100 no devnet), todo node recalcula
`Bits` de forma independente e determinística:

```
novoTarget = targetAtual × (tempoRealDaJanela / tempoEsperadoDaJanela)
tempoEsperadoDaJanela = RetargetInterval × TargetSpacing   // 100 × 60s no devnet
```

com duas guardas obrigatórias:

1. **Clamp de ajuste em [¼×, 4×]** por época: mesmo que o tempo real da
   janela seja muito maior ou menor que o esperado, o ajuste desta rodada
   não pode multiplicar ou dividir o target por mais que 4×. Protege contra
   um salto catastrófico de dificuldade causado por timestamp manipulado ou
   variação brusca de hashrate.
2. **Piso em `PowLimitBits`**: o target resultante nunca pode ficar acima do
   limite mínimo de dificuldade da rede (equivalente a dizer que a
   dificuldade nunca cai abaixo de um piso).
3. **`tempoRealDaJanela` nunca é usado como 0 ou negativo na divisão.**
   Timestamps invertidos (`last < first`, possível numa janela curta ou
   timestamp adversarial) devem ser clampados a um mínimo positivo antes da
   divisão — nunca propagados. Estabilidade numérica aqui **é regra de
   consenso**: um node que dividisse por zero e outro que clampasse
   divergiriam sobre o próximo `Bits`, e a rede se partiria.

Rede cresceu → blocos chegam rápido demais → janela real menor que a
esperada → target cai → mais difícil → volta a ~`TargetSpacing` por bloco.
O ritmo de emissão fica imune ao tamanho da rede.

### Verificação parcial durante IBD

Um node em sincronização inicial (Initial Block Download, ver ZEN-004) **não
verifica o Argon2id de cada header individualmente** — Argon2 é caro demais
para rodar por header numa sincronização de milhares de blocos. A checagem
completa de PoW acontece quando o bloco inteiro é validado e conectado (ver
ZEN-003). Um node conforme não pode pular essa checagem completa no
connect — só pode adiá-la para depois do download dos headers.

## Casos de erro

- `Bits` malformado (mantissa ou expoente fora de faixa ao decodificar) →
  target inválido, bloco rejeitado.
- `target == 0` → tratado como inválido (evita divisão por zero em
  `BlockWork`).
- Timestamps invertidos na janela de retarget (`last < first`) → clampar no
  mínimo definido, nunca dividir por zero ou por número negativo.

## Compatibilidade

Mudar o algoritmo de hash (Argon2id → outro), os parâmetros de memória/tempo
por perfil já fixados, o salt, ou a fórmula/clamp de retarget é incompatível
com a rede existente: nodes com regras diferentes calculam `PowHash` ou
`Bits` esperado diferente e se rejeitam mutuamente. Qualquer mudança aqui é
hard fork / rede nova, análoga a mudar o perfil em `params` (ZEN-005).
