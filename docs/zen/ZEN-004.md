# ZEN-004: Protocolo de rede P2P

`final`

## Resumo

Define o framing de fio, o envelope de mensagem, o handshake, os tipos de
mensagem e as regras de gossip/sincronização que fazem dois nodes Zhu
conversarem — a camada que qualquer reimplementação precisa falar para se
conectar à rede.

## Motivação

Não existe servidor central: a rede se sustenta porque cada node conversa
com um punhado de peers e informação se espalha por fofoca (gossip). O
protocolo é TCP puro + um envelope JSON próprio — sem libp8p — porque, para
o propósito do projeto, um framing auditável de ponta a ponta (sem
multiplexação/criptografia/descoberta escondidas numa lib) cabe na cabeça de
quem está aprendendo e ainda assim é suficiente para uma rede real.

## Especificação

### Framing (fio)

Sobre `net.Conn` (ou qualquer `io.ReadWriter`):

```
frame = uint32_BE(tamanho_do_payload) ‖ payload_JSON
```

- **Tamanho máximo de frame: 1 MiB.** O tamanho vem antes do payload
  justamente para que o tamanho seja validado **antes de alocar o buffer** —
  um peer malicioso anunciando um tamanho gigante não deve fazer o
  destinatário alocar memória proporcional antes de rejeitar. 1 MiB é
  folgado frente ao bloco máximo de consenso (256 KiB, ZEN-005/ZEN-003).
- Payload é sempre JSON, nunca binário de fio próprio: o consenso já tem
  serialização canônica em bytes (ZEN-001); o transporte não precisa ser
  compacto, precisa ser inspecionável (um `tcpdump` dá para ler).

### Envelope de mensagem

```json
{ "Type": "<tipo>", "Payload": <json qualquer> }
```

Blocos e transações, quando aparecem dentro de `Payload`, viajam como os
bytes canônicos de ZEN-001 codificados em **base64** dentro do JSON — não
reserializados em JSON campo a campo.

Um `Type` desconhecido **é ignorado silenciosamente**, nunca causa erro ou
desconexão — isso é o que permite que binários antigos continuem
compatíveis quando tipos de mensagem novos forem introduzidos por um ZEN
futuro.

### Tipos de mensagem

`version`, `verack`, `ping`, `pong`, `getaddr`, `addr`, `inv`, `getdata`,
`getheaders`, `headers`, `block`, `tx`, `reject`, `getmempool`.

### Handshake

**Nenhuma mensagem é processada antes do handshake `version`+`verack`
completo.** O payload de `version`:

| Campo | Tipo | Observação |
|-------|------|------------|
| protocol | uint32 | versão do protocolo (1) |
| genesis | hex, 32 bytes | ID do bloco gênesis do perfil (ZEN-001/ZEN-005) |
| height | uint64 | altura da ponta local |
| cum_work | hex | trabalho acumulado local (ZEN-002) |
| listen_addr | string | endereço anunciável deste node, se aceita entrada |
| nonce | uint64 | valor aleatório para detectar auto-conexão |

Regras do handshake:

- **`genesis` diferente → `reject` e desconectar.** É a definição de "estar
  na mesma rede": um hash de gênesis diferente (ZEN-005: perfis/builds
  distintos produzem gêneses distintos) significa protocolo/economia
  incompatível.
- **`nonce` igual ao próprio nonce gerado → drop silencioso** (é
  auto-conexão, o node discou para si mesmo).
- Depois do handshake, cada lado sabe a altura e o trabalho acumulado do
  outro e decide se precisa sincronizar (abaixo).

### Sincronização (IBD — Initial Block Download)

Disparada quando `cum_work` do peer é maior que o local (o mesmo critério de
fork choice de ZEN-003 — nunca comparar por altura, senão um peer com cadeia
longa e fraca arrastaria o node para o ramo errado):

1. **Headers-first**: pedir com `getheaders` usando um *locator* — lista de
   hashes de blocos espaçados exponencialmente a partir da ponta local, para
   achar o ponto em comum com o peer em O(log n) mensagens em vez de
   enumerar a cadeia inteira.
2. Receber até 2.000 headers de header em `headers`; validar encadeamento e
   `Bits` (ZEN-002/ZEN-003) — **sem** rodar o Argon2id caro por header
   (adiado para quando o bloco completo chegar, conforme ZEN-002).
3. Pedir os corpos dos blocos via `getdata`, em janelas de 16, e conectá-los
   em ordem (validação completa, ZEN-003).

**Steady-state** (fora de IBD): `inv` anuncia o que o node tem ("tenho o
bloco X / a tx Y"); quem não tem, pede com `getdata`; a resposta chega como
`block` ou `tx`. Isso evita empurrar dados que o peer já possui.

- Bloco recebido → `chain.AcceptBlock` (ZEN-003). Se órfão, dispara
  `getheaders` de volta ao peer de origem. Se inválido, `reject` (sem ban
  score nesta versão — evolução futura).
- Tx recebida → tenta entrar no mempool; se aceita, é re-anunciada via `inv`
  a todos os peers **exceto o de origem** (evita eco).
- Bloco novo minerado ou conectado localmente → `inv(block)` a todos os
  peers.
- Dois peers anunciando o mesmo bloco/tx → **um único `getdata`**
  deduplicado por ID, não um por peer.
- `getmempool`: enviado no máximo 1× por conexão — no handshake se o node já
  está em dia com o peer, ou ao fim do IBD (pendências não validariam
  antes). Resposta: `inv` com até 1.000 TxIDs (maior taxa por byte primeiro);
  o fluxo normal `getdata`→`tx` completa a transferência.

### Descoberta e address book

- **Outbound-only é cidadão pleno.** O protocolo não pode assumir que peers
  são alcançáveis de fora (a maioria dos nodes domésticos está atrás de
  NAT/CGNAT). Um node que só disca para fora valida, minera e propaga
  normalmente. Máximo de 8 conexões outbound simultâneas.
- **`getaddr`/`addr`**: troca de endereços de outros peers conhecidos, até
  32 endereços por mensagem. O address book só anuncia o `listen_addr` de
  peers que **declararam** aceitar entrada no handshake — não polui a rede
  com endereços inalcançáveis.
- **Relay contínuo de endereços novos**: um endereço aprendido pela primeira
  vez (no handshake ou num `addr` recebido) é re-anunciado na hora aos
  demais peers conectados — não só no handshake inicial. Isso permite que um
  node recém-chegado seja conhecido pela rede inteira sem que ninguém
  reconecte, e que a rede sobreviva à queda do seed original. Um endereço já
  conhecido (eco) **não** é re-relayado — é o que faz o gossip convergir em
  vez de circular indefinidamente.
- Como redundância para relays perdidos, um `getaddr` extra é enviado a um
  peer sorteado a cada `AddrInterval` (10 minutos).
- **Address book — backoff exponencial e evicção:** cada endereço guarda
  `Fails`/`NextTry`/`LastSeen` (estado de runtime; só a lista de endereços é
  persistida). Falha de dial dobra a espera até a próxima tentativa
  (15s → 30s → ... → 1h). Na 10ª falha consecutiva, o endereço é evicto do
  book — **exceto seeds** (endereços passados via `-peers`), que entram em
  backoff mas nunca são removidos, pois são a âncora de conectividade
  configurada pelo dono do node. Com o book cheio (256 endereços), aprender
  um endereço novo evicta a pior entrada não-seed (mais falhas; empate →
  visto há mais tempo) em vez de descartar o novo — senão lixo anunciado por
  um peer malicioso ocuparia as vagas para sempre. Reaprender um endereço já
  conhecido **não** reseta o backoff dele (re-anunciar um endereço morto não
  o ressuscita).
- **Ping/pong**: a cada 2 minutos; peer que não responde a 2 pings seguidos
  é desconectado, e o peer manager redisca do address book respeitando o
  backoff do endereço.

### Proxy e endereço anunciado

Toda conexão de saída pode passar por um proxy SOCKS5 (tipicamente Tor
local, que resolve `.onion`). O endereço anunciado no handshake
(`listen_addr`) é desacoplado do endereço de bind local — um hidden service
anuncia seu `.onion`, não o `127.0.0.1` do bind. Por isso o protocolo não
define criptografia de transporte própria nesta versão: via Tor, o
transporte já sai cifrado de ponta a ponta pelo próprio onion.

## Casos de erro

- Frame acima de 1 MiB → desconectar sem alocar o payload.
- Mensagem antes do handshake completo → ignorada/conexão fechada.
- `genesis` ou `protocol` incompatível no `version` → `reject` + drop
  imediato.
- `nonce` de auto-conexão → drop silencioso.
- Headers que não encadeiam ou com `Bits` incorretos → drop do peer que os
  enviou.
- Peer sem resposta a ping 2× seguidas → drop; reconexão via address book.

## Compatibilidade

Mudar o framing, os campos obrigatórios do `version`, ou o critério de
rejeição do handshake é incompatível com nodes existentes. Novos tipos de
mensagem são **aditivos e compatíveis por construção**, porque um `Type`
desconhecido é ignorado em vez de causar erro — um ZEN futuro pode introduzir
`compactblock` ou similar sem quebrar nodes antigos, desde que o fluxo
`inv`/`getdata` continue funcionando como fallback.
