# ZEN-003: Validação de bloco e fork choice

`final`

> **Nota:** a cláusula de taxas na regra 8 (abaixo) está proposta para
> substituição por [ZEN-011](./ZEN-011.md) (`draft`) — o teto da coinbase
> passaria a ser só o subsídio, sem `+ Σ taxas do bloco` (taxas seriam
> queimadas). Este ZEN continua `final` e vale como está até ZEN-011 (e
> [ZEN-009](./ZEN-009.md), que redefine o próprio subsídio) serem
> implementados e promovidos a `final`.

## Resumo

Define a sequência completa de checagens que fazem um bloco válido, o
critério de qual cadeia é "a verdadeira" quando a rede bifurca (fork), e como
um node troca de cadeia (reorg) sem corromper seu estado.

## Motivação

Não existe coordenador central decidindo qual bloco entra na história; cada
node decide sozinho, aplicando exatamente as mesmas regras, que ele
converge com todos os outros nodes honestos. Se a lista de checagens ou o
critério de fork choice divergir entre implementações, a rede se parte em
silêncio — dois nodes aceitam históricos diferentes e nenhum dos dois sabe.
Este ZEN é o texto que qualquer reimplementação precisa seguir à risca.

## Especificação

### Sequência de validação de um bloco

Um bloco só é aceito se, nesta ordem, passar por:

1. **Header**: PoW válido (`pow.CheckProofOfWork`, ZEN-002); `Bits` é
   exatamente o esperado para a altura (considerando o retarget na fronteira
   de `RetargetInterval` blocos); `Timestamp` maior que a mediana dos
   últimos 11 blocos (**MTP-11**, abaixo) e menor que `agora + 2 minutos`.
2. **`PrevHash` conhecido**: se o pai não está na cadeia local, o bloco vai
   para o *orphan pool* (abaixo) e o node pede o pai ao peer de origem — não
   é rejeitado definitivamente, só adiado.
3. **Tamanho**: bloco serializado (ZEN-001) ≤ `MaxBlockSize` (256 KiB,
   ZEN-005) — regra de consenso, não config; protege disco e banda do node
   caseiro.
4. **Estrutura de transações**: merkle root bate com os TxIDs
   (ZEN-001); `Txs[0]` é coinbase e é a **única** coinbase do bloco; a
   coinbase embute a altura no input (estilo BIP34, ZEN-001) — sem isso duas
   coinbases idênticas colidiriam no UTXO set.
5. **Cada input existe e não foi gasto** — inclusive contra gastos feitos
   por *outra transação do mesmo bloco* (double-spend intra-bloco, abaixo).
6. **Assinatura**: ECDSA válida por input contra o sighash (ZEN-001);
   `SHA-256(PubKey)[:20]` deve bater com o `PubKeyHash` do output sendo
   gasto.
7. **Maturidade da coinbase**: um output de coinbase só pode ser gasto depois
   de `CoinbaseMaturity` blocos (10 no devnet, ZEN-005) confirmados sobre
   ele.
8. **Conservação de valor**: por transação, `Σ inputs ≥ Σ outputs`
   (aritmética sem overflow, checagem explícita — nunca confiar em wraparound
   silencioso de `uint64`); a diferença é a taxa. Para a coinbase:
   `coinbase.value ≤ subsídio(altura) + Σ taxas do bloco` (ver ZEN-005 para
   `BlockSubsidy`).
9. **Gênesis é exceção**: o bloco de altura 0 não passa pelas regras acima —
   é validado só por **hash exato** contra o gênesis hardcoded do perfil
   (ZEN-005). Ele não tem pai nem histórico contra o qual se validar; *é* o
   ponto de partida do acordo, e seu hash funciona como identidade da rede no
   handshake P2P (ZEN-004).

Se todas as checagens aplicáveis passam, o bloco é **conectado**: os UTXOs
que ele gasta são removidos do UTXO set, os que ele cria são adicionados, e
o "undo set" do bloco (o que foi consumido) é persistido para permitir
desfazer depois. Conectar um bloco é atômico — ou entra inteiro, ou não
entra; um node nunca fica com o UTXO set parcialmente atualizado.

### MTP-11 (Median Time Past)

Timestamp de bloco é auto-declarado pelo minerador — sem regra, ele poderia
mentir para manipular o retarget (ZEN-002). A defesa: o timestamp do bloco
precisa ser estritamente maior que a **mediana dos timestamps dos últimos 11
blocos** (não o último isolado, que é manipulável sozinho) e menor que
"agora + 2 minutos" (tolerância de clock drift entre nodes). Isso limita a
fraude de timestamp a uma janela estreita.

### Double-spend intra-bloco

Validar cada input só contra o UTXO set persistido no disco não é
suficiente: dois inputs *do mesmo bloco* poderiam apontar para o mesmo
output sem que nenhum dos dois veja o outro como "já gasto" no UTXO set
(que só é atualizado depois que o bloco inteiro é aceito). A validação
precisa rastrear, dentro do próprio bloco sendo validado, todo output já
consumido por um input anterior do mesmo bloco, e rejeitar o segundo gasto.

### Fork choice: trabalho acumulado, não altura

Quando dois blocos válidos disputam a mesma altura (dois mineradores
acharam blocos quase juntos), a rede bifurca. Cada node guarda os dois
ramos. A cadeia ativa (a "verdadeira" do ponto de vista deste node) é
sempre a de **maior trabalho acumulado** (`cumWork`, soma de `BlockWork` por
bloco — ZEN-002) — **nunca a mais longa em número de blocos**. Altura é
falsificável barato (encadear muitos blocos de dificuldade mínima); trabalho
reflete custo real de energia/memória e não é.

### Reorg

Quando um ramo lateral ultrapassa o `cumWork` da ponta ativa, o node faz
reorg:

1. **Desconecta** os blocos do ramo perdedor, do mais recente até o ponto de
   bifurcação em comum, restaurando o UTXO set com o *undo set* de cada
   bloco desconectado (os outputs que ele havia gasto voltam a existir como
   não-gastos; os que ele criou são removidos).
2. **Conecta** o ramo vencedor, bloco a bloco, a partir do ponto de
   bifurcação — **revalidando cada bloco por inteiro de novo**, não
   assumindo que um bloco já validado antes continua válido no novo
   contexto de UTXO. Um bloco do ramo lateral que gastava um UTXO só
   disponível naquele ramo pode se tornar inválido no contexto do ramo
   vencedor.
3. Transações que ficaram órfãs do ramo perdedor voltam ao mempool para
   tentar entrar num bloco futuro.

Pular a revalidação completa do passo 2 abriria a porta para aceitar um
double-spend que só fica visível depois da troca de ramo.

### Orphan pool

Um bloco cujo `PrevHash` ainda não é conhecido (o pai não chegou, ou chegou
fora de ordem) é guardado num pool à espera, limitado a ~100 entradas com
descarte FIFO (o mais antigo sai quando o pool enche). Sem esse limite, um
peer malicioso poderia inundar a memória de um node com órfãos que nunca se
resolvem — o cap troca completude por uma superfície de negação de serviço
fechada.

## Casos de erro

Cada regra de validação acima corresponde a um erro específico e testável
(não um erro genérico "bloco inválido"). Casos notáveis:

- Bloco já conhecido (duplicado) → no-op, não é erro.
- `PrevHash` desconhecido → orphan pool, não rejeição definitiva.
- Reorg profundo → o UTXO set após o reorg deve ser idêntico a um replay do
  zero até o mesmo tip (invariante que qualquer implementação deve poder
  testar).
- Crash no meio de um connect de bloco → como o connect é atômico, o node
  reabre no estado anterior ao connect (nunca parcialmente aplicado).

## Compatibilidade

Mudar qualquer item da sequência de validação, o critério de fork choice
(trabalho em vez de altura), ou a regra de MTP-11 é hard fork: nodes com
regras diferentes aceitam/rejeitam blocos de forma diferente e divergem
permanentemente. Adicionar checkpoints hardcoded ou pruning no futuro
(hoje fora de escopo — ver `internal/chain/SPEC.md`) exigiria um ZEN próprio.
