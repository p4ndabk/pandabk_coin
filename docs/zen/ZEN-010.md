# ZEN-010: Queima estrutural com commitment de 32 bytes

`draft` · `consenso`

## Resumo

Define um novo tipo de output — o **output de queima** — que destrói valor
permanentemente (nunca entra no UTXO set, nunca pode ser gasto por
ninguém) e carrega um **commitment de 32 bytes**: o hash de uma ação de
aplicação feita fora da chain (publicar um post, entrar numa sala, curtir
um artigo). O protocolo não entende nem guarda o conteúdo da ação — só
prova, de forma imutável e datada por bloco, que **alguém pagou um custo
real e irrecuperável em ZHU para registrar aquele hash**.

## Motivação

O piso de emissão perpétua de [ZEN-009](./ZEN-009.md) resolve "a rede
nunca fica sem subsídio para minerador", mas sozinho só cria supply
crescente sem limite — exatamente o cenário de inflação que o autor deste
ZEN quer evitar. A resposta não é voltar a um teto fixo (que reintroduziria
o incentivo a açambarcar em vez de usar), mas dar à rede um **sorvedouro**
proporcional ao uso real: toda ação de aplicação que "gasta" ZHU para
existir (postar, entrar numa sala, curtir) queima aquele valor em vez de
pagá-lo a alguém. Quanto mais a rede é usada, mais ZHU sai de circulação —
um contrapeso deflacionário controlado pela demanda, não por uma constante
arbitrária. É também, de graça, uma defesa antispam: publicar deixa de ser
grátis.

**Por que só um commitment, não o conteúdo:** o projeto já tem uma regra
dura de `MaxBlockSize = 256 KiB` (ZEN-005) pensada para o node doméstico
("um node em cada casa" — PLAN.md). Gravar posts/curtidas inteiros on-chain
competiria por esse orçamento e trairia esse princípio a cada ação social.
Gravar só o hash mantém a chain do tamanho de sempre — o conteúdo real vive
em outro sistema (a aplicação escolhe onde), e a chain garante só duas
coisas: que o hash existe desde um certo bloco, e que custou uma queima
real para colocá-lo lá.

## Especificação

### Formato do output (extensão de `TxOut`, ZEN-001)

```
TxOut {
    Value      uint64      // como hoje
    Type       byte        // 0 = pay-to-pubkey-hash (default, formato atual); 1 = queima
    PubKeyHash [20]byte    // presente e obrigatório só se Type == 0
    Commitment [32]byte    // presente e obrigatório só se Type == 1
}
```

Serialização canônica (big-endian, ZEN-001): `Value(8) ‖ Type(1)`, seguido
de `PubKeyHash(20)` se `Type == 0`, ou `Commitment(32)` se `Type == 1` —
**comprimento variável por tipo**, não os 61 bytes fixos de sempre incluir
os dois campos. Isso evita inflar toda transação normal (a maioria) em 32
bytes só para acomodar um recurso que só uma minoria dos outputs usa —
consistente com o princípio de bloco pequeno acima. `Type` fora de `{0,
1}` → transação estruturalmente inválida.

### Regras de negócio

1. **Output de queima nunca entra no UTXO set.** No connect do bloco
   (ZEN-003), outputs com `Type == 1` são contados normalmente do lado
   `Σ outputs` da conservação de valor (regra 8 de ZEN-003), mas **não são
   inseridos** no bucket `utxo` — o valor é destruído no mesmo instante em
   que o bloco conecta, de forma tão explícita e auditável quanto uma taxa,
   só que sem destinatário. (Mesmo que fossem inseridos, ninguém teria a
   chave para gastá-los — nenhum `PubKeyHash` real gera um `Commitment` de
   32 bytes por definição de formato — mas excluir do UTXO set direto
   também evita inchar o índice com lixo permanentemente não-gasto.)
2. **`Value` de um output de queima deve ser > 0.** Queima de valor zero
   não custa nada e não é uma queima — só um registro grátis, reabrindo a
   porta de spam que este ZEN existe para fechar.
3. **Uma transação pode ter múltiplos outputs de queima** (misturados com
   outputs normais de troco) — permite uma aplicação registrar várias
   ações num único envio.
4. **O `Commitment` é opaco ao protocolo.** Nenhuma regra de consenso
   interpreta os 32 bytes — o esquema de hash (o que exatamente vai
   dentro: hash do post, `hash(sala ‖ participante ‖ timestamp)`, etc.) é
   definido pela aplicação por cima, não por este ZEN. O que o protocolo
   garante é só: existência a partir de um bloco/altura específico, e o
   `Value` queimado junto.
5. **Ordem/datação**: a posição do commitment na chain (altura do bloco +
   posição da tx) funciona como carimbo de tempo verificável para a ação —
   qualquer um pode provar "esta ação existia até, no mais tardar, o bloco
   N" apontando para a transação de queima.

### Coinbase não pode ser output de queima

A transação coinbase (ZEN-001/ZEN-003) continua seguindo suas próprias
regras estruturais; `Type == 1` não é uma forma válida de output de
coinbase nesta versão — a queima é uma ação de quem *gasta* ZHU, não de
quem o emite.

## Casos de erro

- `Type` diferente de 0 ou 1 → tx estruturalmente inválida, rejeitada
  antes de qualquer outra checagem (mesmo nível de severidade que "tx com
  0 outputs" em ZEN-001).
- Output de queima com `Value == 0` → tx inválida.
- Output `Type == 0` com `Commitment` presente, ou `Type == 1` com
  `PubKeyHash` presente → erro de serialização/decodificação (o campo
  errado para o tipo não deve nem aparecer nos bytes).
- Tentativa de gastar um output de queima → impossível por construção (não
  está no UTXO set); um `getnewutxos`/`getbalance` (ZEN-008) nunca deve
  listá-lo.

## Compatibilidade

**Hard fork.** `Type` é um campo novo no meio do formato canônico de
`TxOut` (ZEN-001) — um node que não conhece este ZEN não consegue nem
decodificar uma transação com um output de queima (o layout de bytes
mudou), então não há caminho de soft-fork opcional aqui: é rede nova junto
com [ZEN-009](./ZEN-009.md), não uma extensão isolada.

## Questões em aberto (antes de sair de `draft`)

- Deve existir um **piso mínimo de queima** (ex.: "toda ação custa pelo
  menos 0.01 ZHU") fixado em `params`, ou o valor fica livre por
  transação (a própria aplicação decide, e o mercado/spam-resistência vem
  só do custo marginal de qualquer valor > 0)?
- O RPC do node (ZEN-008) precisa de um método novo para consultar
  commitments de queima por altura/intervalo (uma espécie de índice de
  "registro de ações"), ou isso fica inteiramente por conta da aplicação
  escanear blocos?
