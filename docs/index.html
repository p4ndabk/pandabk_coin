Zhu Network

Descentralizados e unidos!

Uma rede onde cada casa tem luz própria. Por baixo, uma blockchain proof-of-work memory-hard (Argon2id) desenhada para uma única obsessão — um node em cada casa: a mineração cabe num notebook usado, num Raspberry Pi, num PC antigo. O gargalo é RAM comum, não hardware specializado.

Argon2id PoW UTXO Go 1.25 bbolt TCP + JSON P2P ECDSA P-256 1 binário estático

Introdução #

A Zhu segue os paradigmas do Bitcoin — proof of work, halving, descentralização — mas com um diferencial central: mineração acessível a qualquer máquina comum, com baixo consumo de energia e sem centralização em ASICs ou fazendas.

A resposta técnica é um PoW memory-hard (Argon2id): o gargalo vira banda de memória RAM (commodity) em vez de FLOPS. Um notebook compete de igual pra igual e ASIC não compensa — mesma filosofia do RandomX do Monero.

Assim como o bambu é a energia simples e abundante que sustenta a vida de baixo consumo do panda, a RAM comum é o "bambu" da rede — qualquer casa tem, ninguém precisa de uma usina para participar.

O repositório

O node vive num binário standalone cmd/node (módulo zhu), sem Gin nem GORM, com storage próprio em bbolt. O skeleton Gin+GORM fica intocado e compilando — pode virar block explorer no futuro.

Um node em cada casa #

A meta é ser a rede mais descentralizada possível: qualquer pessoa deve conseguir rodar um full node em casa — sem sentir. Descentralização não é discurso, é orçamento de recursos. Todo trade-off se decide por esta régua: "isso deixa mais fácil ou mais difícil ter um node em casa?"

RecursoOrçamentoComo
Instalação1 binário estático, zero depsCGO_ENABLED=0; cross-compile linux/darwin/windows, amd64+arm64

RAMidle < ~128 MiB; +64 MiB/workera matriz do Argon2 é o maior consumidor, e é limitada por config

Com PoW memory-hard, a segurança vem da quantidade de participantes, não da potência de cada um. "Um node em cada casa" implica "cada casa minera um pouco" — cada pessoa que sobe um node acende o seu lume.

Layout de pacotes #

Direção de dependência estrita: cada camada só usa as de baixo. Structs concretos, wiring manual em cmd/node/main.go, sem interfaces/DI.

params ← core ← pow ← chain ← {mempool, wallet} ← {p2p, miner} ← node ← cmd/node

cmd/node/main.go     # dispatch de subcomandos, wiring manual
internal/params/     # Params + perfis DevNet/MainNet, BlockSubsidy, genesis
internal/core/       # block, tx (UTXO), merkle, encoding canônico, address
internal/pow/        # argon2 (PowHash), target, retarget
internal/chain/      # store (bbolt), AcceptBlock, validate, forkchoice, orphans
internal/mempool/    # pool por txid, anti double-spend, ordenação por fee
internal/wallet/     # keygen P-256, wallet.json (0600), BuildTx
internal/p2p/        # message, codec, peer, server, sync (IBD)
internal/miner/      # worker pool (default 1), template, restart em novo tip
internal/node/       # config, node (Start/Stop), rpc (localhost)

Spec-first

Cada pacote tem sua própria SPEC.md, com uma seção didática de "Conceito" — o usuário aprende blockchain lendo o projeto. Non-goals explícitos em cada spec: sem scripts, sem SPV, sem criptografia de wallet v1, sem NAT traversal, sem explorer.

O full node #

O full node é a unidade de soberania da rede: valida tudo por conta própria (não confia em ninguém), guarda a cadeia inteira, serve outros nós e minera por padrão com 1 worker. Rodar um node é o ato que descentraliza a rede.

O processo junta quatro subsistemas ligados pelo Node, montados à mão (igual ao cmd/api/main.go faz com seus serviços):

  • chain — o estado: valida e persiste blocos, mantém o UTXO set, faz reorg.
  • mempool — a fila de transações pendentes.
  • p2p — a rede: handshake, gossip, sincronização.
  • miner — opcional (default ligado): produz blocos novos.

Shutdown em ordem estrita

p2p → miner → bbolt. Fechar o banco antes de parar quem escreve nele (miner e p2p aceitando blocos) corromperia uma transação em voo. A ordem não é estética — é o que garante que um SIGINT durante o IBD deixe o disco consistente.

PoW memory-hard #

Cada bloco só é válido se o hash de PoW do seu header ficar abaixo do alvo. O hash de PoW é Argon2id — memory-hard de verdade — enquanto o ID do bloco é um SHA-256d barato do mesmo header. Separar os dois é o padrão de moedas memory-hard: o índice nunca recomputa Argon2.

PowHash = Argon2id(header[96B], salt="zhubk/pow/v1")
          mem=64 MiB · time=1 · threads=1 · keyLen=32   // ~100–200 ms/hash em laptop

bloco válido   ⟺   PowHash < target(Bits)
ID do bloco    =   SHA-256d(header)          // barato, ≠ hash de PoW

Com Argon2id não há incentivo pra escalar hardware: o custo por participante fica fixo e baixo (1 core + 64 MiB por worker). O contraste com o Bitcoin é deliberado — onde o Bitcoin é laranja de energia cara, a Zhu é verde de energia de casa.

Estrutura de dados #

Block header — 96 bytes

Serializado com codificação binária canônica (hashing determinístico — gob/JSON não servem para consenso):

Version   Height   PrevHash   MerkleRoot   Timestamp   Bits(nBits)   Nonce

Transação (UTXO)

Tx é composta de TxIn / TxOut / OutPoint, mais a coinbase. Não há sistema de scripts — só pay-to-pubkey-hash estrutural.

Sighash (SIGHASH_ALL simplificado)

A assinatura cobre o SHA-256d da tx com o campo sig vazio e o slot da pubkey substituído pelo PubKeyHash do output referenciado.

Endereço — Base58Check

versão 0x37  +  SHA-256(pubkey)[:20]  +  checksum SHA-256d[:4]   ──base58──▶  "P..."

Chain & storage #

O estado vive em bbolt (single-file, ACID, pure Go), organizado em buckets KV:

BucketGuarda
blocksblocos completos por hash
blockIndexmetadados/altura por hash
heightIndexhash por altura (cadeia principal)
utxoo UTXO set (saldo verificável)
undoundo sets para reorg
metatip, ponteiros de estado

AcceptBlock valida cada classe de regra antes de conectar: PoW, merkle root, timestamps (MTP-11 / +2 min), coinbase = subsidy + fees, existência de UTXO, assinaturas, e maturidade de coinbase (10 blocos). Forks se resolvem por trabalho acumulado; o reorg desfaz blocos via undo sets e reaplica a cadeia vencedora.

Dificuldade & retarget #

A cada 100 blocos, todo nó faz a mesma conta determinística:

novo alvo = alvo atual × (tempo real dos últimos 100 blocos ÷ 100 min esperados)
            // com clamp de 4× / ¼× por retarget
trabalho  = 2^256 / (target + 1)
  • Rede cresceu → blocos rápidos demais → alvo cai → mais difícil → volta a ~60 s/bloco.
  • Rede encolheu → blocos lentos → alvo sobe → mais fácil → volta a ~60 s/bloco.
  • O ritmo de emissão (e o halving) é imune ao tamanho da rede.

Mempool #

Pool de transações pendentes validado por txid, com proteção anti double-spend e ordenação por fee rate. Transações são removidas quando o bloco que as inclui conecta (evict), e restauradas se um reorg desfizer esse bloco (restore).

Wallet & identidade #

Geração de chaves P-256; a chave privada é persistida em wallet.json com permissão 0600. BuildTx faz seleção de UTXOs largest-first, calcula o troco (change) e assina input por input.

A revolução do perfil

Na visão da Zhu, a wallet deixa de ser "arquivo que guarda dinheiro" e vira perfil: uma identidade, dois poderes — valor (Zhu) e voz (Nostr). A camada social não entra na chain (isso mataria "um node em cada casa"); a chave é a ponte, não a chain. Decisão de formato de wallet ainda em aberto: unificar em secp256k1 (endereço Zhu + npub) ou manter P-256 e derivar a chave Nostr do mesmo seed.

Protocolo P2P #

TCP puro, envelope JSON com length-prefix de 4 bytes (frame máx 1 MiB). Máximo de 8 peers. O codec é testável com net.Pipe.

// handshake     version · verack
// keepalive    ping · pong
// descoberta   addr · getaddr
// gossip       inv · getdata · block · tx
// sync (IBD)   getheaders · headers
// erro         reject

O hash do genesis vai no handshake version como ID da rede — é assim que todos concordam no bloco 0 e rejeitam nós de outra chain.

Sincronização (IBD) #

Initial Block Download: o nó pede getheaders com um locator, recebe os headers (96 B cada) e então baixa os corpos em janelas de 16. O Argon2 é verificado no bloco completo, não no header isolado. Forks convergem para a cadeia de mais trabalho.

A voz do Zhu no CLI

Durante o IBD, o node fala como o guardião: Zhu está sincronizando os blocos — vá tomar um café. Quando sobe: Lanterna acesa. Sem peers: Nenhum vizinho encontrado ainda. Zhu continua procurando.

Tor & privacidade #

O node tem suporte nativo a Tor — esconde o IP dos dois lados (de quem conecta em você e de quem você conecta), sem torsocks, igual em Linux, macOS e Windows. É a resposta para NAT/CGNAT e para não expor porta nenhuma. Dois flags fazem tudo:

  • -proxy — roteia toda conexão de saída pelo SOCKS5 do Tor (e é o Tor quem resolve os .onion).
  • -advertise — faz um hidden service anunciar o seu .onion aos peers, em vez do endereço local.

1 · Instalar o Tor

sudo apt install tor          # Linux (Debian/Ubuntu)
brew install tor              # macOS
# Windows: "Tor Expert Bundle" (torproject.org)

2 · Receber conexões como hidden service

Aponte um serviço onion para a porta P2P local, no torrc (/etc/tor/torrc no Linux, /opt/homebrew/etc/tor/torrc no macOS Apple Silicon):

# torrc
HiddenServiceDir /var/lib/tor/zhu/
HiddenServicePort 9551 127.0.0.1:9551

Reinicie o Tor (sudo systemctl restart tor / brew services restart tor), leia o seu endereço onion e suba o node aceitando só o Tor local, anunciando o .onion:

sudo cat /var/lib/tor/zhu/hostname     # → zhuxyz...def.onion

# mundo externo não vê a porta — só o onion chega, via Tor
zhu run -listen 127.0.0.1:9551 -advertise zhuxyz...def.onion:9551

Compartilhe zhuxyz...def.onion:9551 com os amigos — sem -advertise o node anunciaria o 127.0.0.1 local (inútil para os outros); com ele, o peer exchange espalha o seu onion pela rede.

3 · Conectar em peers .onion

Quem disca para um .onion aponta o -proxy para o SOCKS5 do Tor local (porta 9050) — o destino é resolvido pelo próprio Tor, nenhum IP vaza:

zhu run -proxy 127.0.0.1:9050 -peers zhuxyz...def.onion:9551 -listen ""

No zhu.conf são as chaves proxy= e advertise= (e há env ZHU_PROXY / ZHU_ADVERTISE). Faça os dois lados — hidden service e -proxy — e ninguém expõe IP.

Trade-offs honestos

Latência via Tor é maior e o circuito demora alguns segundos para nascer: o sync inicial fica mais lento. Com -proxy, toda a saída passa pelo Tor de propósito (para não vazar) — se o daemon tor não estiver rodando, o node fica sem peers. Para uma rede de amigos em LAN, Tor é opcional; para atravessar 4G/CGNAT sem abrir porta, é a saída.

Miner #

Worker pool com 1 worker por padrão (~64 MiB de Argon2). Monta o template a partir do mempool (transações ordenadas por fee), busca um nonce válido, e reinicia assim que um novo tip aparece. A coinbase paga a wallet do datadir.

minera por padrão opt-out: --mine=false workers: --miners N

RPC & CLI #

A CLI conversa com o node em execução via RPC JSON em localhost — necessário porque o bbolt aceita um único processo escritor. zhu balance não pode abrir o banco enquanto o node roda, então pergunta pela porta RPC.

Segurança por construção

A RPC é a interface de controle do dono, não uma API pública. O bind é exclusivo em 127.0.0.1 — recusa qualquer bind fora de loopback. Não há autenticação justamente porque não há como alcançá-la de fora.

POST /rpc   {"method": "...", "params": {...}}
         →  {"result": ...}   |   {"error": {"code","message"}}

// métodos
getinfo · getpeers · getbalance · getnewutxos · sendrawtx · sendtoaddress

Subcomandos do binário: run, wallet new, wallet address, balance, send, info, peers, genesis (dev-only: minera o gênesis).

zhu peers mostra a vizinhança do node: cada peer conectado com endereço, direção (entrada = ele conectou em você; saída = você discou), altura declarada no handshake e tempo de conexão. Com -known, lista também o address book — endereços aprendidos por peer exchange, mesmo desconectados. No app desktop, a mesma visão fica na aba Rede.

Build & execução #

# build estático do node
CGO_ENABLED=0 go build -o bin/zhu ./cmd/node

# subir o node (minera por padrão)
bin/zhu run -profile devnet

# CLI via RPC localhost
bin/zhu info | balance | send
bin/zhu powdemo        # bancada didática de mineração

Demo de 2 nodes na mesma máquina

# terminal 1 — minerador
./bin/zhu run --profile devnet --datadir ~/.zhu/n1 --listen :9551 --rpc 127.0.0.1:8551 --mine

# terminal 2 — seguidor
./bin/zhu run --profile devnet --datadir ~/.zhu/n2 --listen :9552 --rpc 127.0.0.1:8552 --peers 127.0.0.1:9551

# terminal 3 — wallet
./bin/zhu wallet new --datadir ~/.zhu/n2
./bin/zhu info    --rpc 127.0.0.1:8552    # alturas convergem ⇒ sync ok
./bin/zhu peers   --rpc 127.0.0.1:8552    # quem está conectado (direção, altura, tempo)
./bin/zhu balance --rpc 127.0.0.1:8551    # cresce conforme coinbases maturam
./bin/zhu send    --rpc 127.0.0.1:8551 --to P... --amount 1.5
./bin/zhu balance --rpc 127.0.0.1:8552    # recebe após o próximo bloco

Sucesso = o node 2 acompanha altura/tip do node 1, e um send do node 1 aparece no saldo do node 2 após confirmação.

Testes #

Cada pacote segue o padrão do repo (service_test.go-equivalente), com go test -race verde. Params de teste (Argon2 de 1 MiB) mantêm a suíte rápida.

CGO_ENABLED=0 go build ./...     # estático, incluindo cmd/api existente
go vet ./... && go test ./...
  • M1 params + core + pow — halving soma = max supply; encode round-trip; merkle; nBits; PoW passa/falha; clamp; sign/verify.
  • M2 chain + storage + genesis — aceita blocos válidos, rejeita cada classe inválida, teste de reorg (fork A(3) vs B(4)).
  • M3 wallet + txs + mempool — endereço round-trip, BuildTx, evict/restore.
  • M4 P2P + sync — handshake em net.Pipe, frame gigante rejeitado, 2 nodes in-process sincronizam.
  • M5 miner + CLI + RPC + docs — mineração solo, template reinicia em novo tip, SIGINT fecha bbolt limpo.
